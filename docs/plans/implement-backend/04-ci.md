## Goal

GitHub Actions checks every push and every pull request. A push to `main` that changes the backend deploys `McpTacticusApi` with the CI role, without the user's machine and without MFA. After the deploy, CI checks that `/health` returns the new commit. The step comes before the first release (step 12). From then on, real players use the API, so each deploy must be repeatable and checked, and must not depend on one machine.

## Scope

In the step:
- `.github/workflows/ci.yml`: install, lint, format check, type checks, tests, Mongo tests, web build, `cdk synth`.
- `.github/workflows/deploy-api.yml`: the checks of `ci.yml`, then the deploy and the health check.

## Decisions that fill gaps in the design

1. **The deploy runs the checks first.** `ci.yml` has the triggers `pull_request`, `push` to `main`, and `workflow_call`. `deploy-api.yml` has the job `checks` with `uses: ./.github/workflows/ci.yml`, and the job `deploy` with `needs: checks`. Reasons:
   - The user commits to `main` and pushes. Most changes have no pull request, so a deploy cannot rely on a pull request check.
   - The list of checks is in one file only.
   - Cost: a push that changes the backend runs the checks twice, once for `CI` and once for `Deploy API`. The repo is public, so the minutes are free.
2. **One job in `ci.yml`.** One install, then the checks in this order: `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm --filter web build`, `pnpm --filter infra synth`, `pnpm --filter api test:mongo`. The fast checks come first, so a lint error fails in seconds. The Mongo tests are last, because they pull the `mongo:8` image. The runner has Docker, so the job needs no service container. `timeout-minutes: 15`.
3. **`pnpm/setup` installs the tools.** It reads pnpm 12.10.0 from `packageManager` and Node 24 from `.node-version`. With `require-lockfile: true` it runs `pnpm install --frozen-lockfile`. Reasons: one action instead of two (`pnpm/action-setup` and `actions/setup-node`), it comes from the pnpm team, and it checks the npm signature of the pnpm binary. Risk 1 has the fallback.
4. **Actions are pinned to a commit SHA.** Each `uses:` has the full SHA and a comment with the version, for example `# v7.0.1`. Reason: the deploy job can assume the CDK deploy role, and that role can change any resource of the account (backend doc, "Security"). A tag can be moved to other code. A SHA cannot. Updates are by hand for now (open question 1).
5. **Least permissions.**
   - Both workflows: top-level `permissions: contents: read`.
   - Only the job `deploy` has `id-token: write`.
   - `actions/checkout` with `persist-credentials: false`. No step pushes to git, so the token does not stay in `.git/config`.
   - `ci.yml` runs on `pull_request`, never on `pull_request_target`. So a pull request from a fork gets no secret and no OIDC token.
6. **Cache.** The job `checks` caches the pnpm store (`cache: true`). The job `deploy` has no cache. Reason: the `actions/setup-node` docs advise no cache in release jobs, because of cache poisoning. The deploy job installs from the registry.
7. **The role ARN is an environment secret, not a variable.** The design says `gh variable set`. This plan changes it to `gh secret set --env prod`. Reasons:
   - The repo is public, so the logs of every run are public.
   - GitHub hides a secret in the logs. It does not hide a variable. The role ARN contains the account id, and the account id is not in git (backend doc, "CDK").
   - `configure-aws-credentials` gets `mask-aws-account-id: true`. Then the account id is hidden in every later log line too, also in the stack ARNs that `cdk deploy` prints.
   - `role-session-name` is `mcptacticus-<run id>`. So CloudTrail shows which run made each change.
   The backend doc changes to match.
8. **The environment `prod` exists before the first push.** The user creates it with `gh api`, with a deployment branch policy that allows only `main`. Reason: GitHub creates a missing environment on its first use, and that environment has no branch rule. The `sub` claim names the environment, so the CI role trusts only jobs of `prod`. The branch rule makes sure that only `main` gets such a job. No required reviewers: the deploy runs on its own, as the design says.
9. **Deploy triggers.** `push` to `main` with these `paths`, and `workflow_dispatch`:

   ```
   apps/api/**
   infra/**
   packages/**
   package.json
   pnpm-lock.yaml
   pnpm-workspace.yaml
   tsconfig.base.json
   .node-version
   .github/workflows/deploy-api.yml
   !**/*.md
   ```

   - The root files change the bundle or the install: root `esbuild` in `package.json`, the lock file, the workspace, the shared TypeScript settings, the Node version.
   - `deploy-api.yml` is in the list, so a change of the deploy is tested at once. The push of this step runs the first CI deploy for this reason.
   - `ci.yml` is not in the list. A change of `ci.yml` runs `CI` on its own push, and it does not need a new deploy.
   - `!**/*.md`: every deploy sets a new `APP_VERSION`, so AWS replaces the Lambda instances. A change of a README needs no deploy.
10. **Deploy command.** The command of "Names", run in the job `deploy` after `configure-aws-credentials`. It does not use the script `cdk:deploy`, because that script has `--profile mcptacticus`. The outputs file is in `$RUNNER_TEMP`, outside the repo, so the tree stays clean. `bin/app.ts` skips `McpTacticusAccount`, because CI has no `BUDGET_EMAIL`. The CI role could not deploy it anyway.
11. **Health check after the deploy.** A shell step:
    - It reads `McpTacticusApi.ApiUrl` from the outputs file with `jq`.
    - It expects `version` to equal `git rev-parse --short HEAD`. `bin/app.ts` runs the same command in the same checkout, so the length of the short SHA is the same.
    - It calls `${url}health` up to 6 times, 5 s apart, until the status is 200, `version` is the expected value and `db` is `ok`. Then it prints the body and ends with success. Otherwise it prints the last body and fails.
    - Reason for the retries: the first request after a deploy is a cold start (SSM, then the first connection to Atlas). One slow or failed first call must not fail the deploy. A real failure still fails after 30 s.
    - A tree with changes gives a version with `-dirty`. Then the check fails, on purpose: CI must deploy only committed code.
12. **Concurrency.** `deploy-api.yml` has `concurrency: { group: deploy-api, cancel-in-progress: false }`. A running deploy is never cancelled. When more runs wait, GitHub keeps only the newest one, and it deploys the newest commit, which has all earlier changes. `ci.yml` has no concurrency group. Reason: `deploy-api.yml` calls it, and a shared group could cancel the checks of a deploy. `timeout-minutes: 15` on the job `deploy`.
13. **No `infra/.env` in CI.** Both workflows set `DEPLOY_REGION` at the top level. `configure-aws-credentials` gets `aws-region: ${{ env.DEPLOY_REGION }}`.
14. **Local deploy stays.** `pnpm --filter infra cdk:deploy` with MFA still works. It is the fallback when GitHub Actions does not work. When a CI deploy runs at the same time, CloudFormation rejects the second update of the stack, so the two cannot mix.

## Risks and open questions

1. **`pnpm/setup` is new.** The repo was created on 2026-05-11, and v3.0.0 came out on 2026-09-20. If it fails, use `pnpm/action-setup` v6.1.0 (it supports pnpm 12) and `actions/setup-node` v7.0.0 with `node-version-file: .node-version`, then `pnpm install --frozen-lockfile`. Record it.
2. **OIDC trust.** If `configure-aws-credentials` fails with `Not authorized to perform sts:AssumeRoleWithWebIdentity`, the `sub` of the token differs from the trust policy. The repo uses the immutable subject format (`use_immutable_subject: true`, checked on 2026-10-09), and the job must have `environment: prod`. Check both before any change of the trust policy.
3. **`cdk synth` without credentials on the runner.** The CDK CLI looks for credentials to find the default account. If the step is slow or fails, set `AWS_EC2_METADATA_DISABLED: true` for the synth step. Record it.
4. **Testcontainers on the runner.** It pulls `mongo:8` from Docker Hub, which has pull limits. If the pull fails often, this needs a decision (for example, a GitHub service container or a registry mirror).
5. **The deploy role is admin.** A deploy from CI can change any resource in the account (backend doc, "Security", and open question 5). Decisions 4, 5 and 8 limit who can start such a deploy.
6. **Cold start in the health check.** Step 3 did not record the cold start time. If the first call takes longer than the 10 s Lambda timeout, the retries of decision 11 hide it once, but it needs a decision. The deploy log shows the times of the calls.
7. **Open question 1: updates of the pinned actions.** Dependabot (`.github/dependabot.yml`, ecosystem `github-actions`) can open pull requests that move the SHA and the version comment. Decide after this step.
8. **Open question 2: workflow checks in CI.** actionlint and zizmor run only once, in phase 1. They can run in `ci.yml` when the workflows change. Decide after this step.
